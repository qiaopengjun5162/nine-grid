01 为什么做这个

拿一个最熟的游戏，
把整条链路走完

A / 复用

规则只写一次

服务端、机器人、链上程序各写一遍判胜，是最容易产生分歧的写法。想验证：一套 core 能不能同时喂给三端。

B / 验证

把规则证明到底

链游 demo 多停在「能转账」，规则本身几乎没人证。九宫棋小到可以 3⁹ 穷举，也小到可以把定理写完。

C / 真实性

让真问题露头

终局冻结、轮次、并发写入、账户租金、钱包网络不一致 —— 这些只有在完整链路上才会真的发生。

规则小到能证完，链路长到能踩坑。

02 它是什么

一个引擎，三个宿主

nine-grid-core 纯规则 · 无 IO · 22 个单测 · 3⁹ 穷举
nine-grid-server

服务端

axum + Postgres。房间码、落子、SSE 观战、回放、战绩榜。

nine-grid-bot

机器人

minimax + α-β 剪枝，三档强度共用一套搜索，只在「怎么挑」上分叉。

nine-grid (Anchor)

链上程序

create / join / play / close。PDA 托管棋局，关局退租金。

判胜只有一份实现：winner() 被三端共同调用。链上账户以 u8 编码，进出都过同一套规则 —— 这也是后面能与 Lean 逐格比对的前提。

01

房间码与邀请链接

三档机器人

八项都能在页面上直接点，不需要安装；只有链上那两项要 Phantom 和一点 Devnet 测试 SOL。

04 验证密度

五层验证，每层挡不同的东西

35个

单元测试

规则对不对。core 22 + bot 13，含 3⁹ 穷举与「机器人 200 局不输」。

44项

端到端冒烟

真 Postgres + 真二进制。服务能不能起来、落库是不是真的、拒绝分支全不全。

11项

链上 E2E

真验证器 + 真交易。完整对局、全部拒绝分支、终局冻结、对局中不许关局、关账户退租金。

3局

浏览器 E2E

模拟 Phantom 走真实 UI：连钱包 → 建局 → 入座 → 落子 → 判胜 → 棋谱馆。

21条

形式化定理

零 sorry。规则在任意输入上成不成立，以及它在什么前提下才成立。

CI 共 8 个 job（fmt / clippy / test / msrv / audit / e2e / chain / lean），每个都在替一句具体的话担保；证明里出现 sorry 直接红灯。

05 形式化

证明最有用的时刻，
是它说「你这句是假的」

随便画一个棋盘

反例存在

O 三连，X 也三连 —— 「双方不可能同时三连」在任意棋盘上是假的。

按规则真下出来的一局

恒成立

终局之后规则拒绝再落子，所以互斥对可达状态恒成立。

所以修 bug 不是加一个 if 兜底，而是把不变量放回状态机 —— 定理 reachable_not_both 说的就是这件事。

06 优劣势

强在规则，弱在产品

优势

  • 01规则单一来源，三端共用；改一处不会各自漂移。
  • 02验证密度高：单测 → 冒烟 → 链上 → 浏览器 → 定理，五层各自兜底。
  • 03前端无需构建：一个静态目录就能跑，Pages 可直接托管。
  • 04可核查：棋谱从交易重建，任何人能自己验一遍。

劣势

  • 01未审计、未上主网，目前只跑在 Devnet。
  • 02服务端没有托管版：想玩本地版得自备 Postgres。
  • 03真机 Phantom 弹窗只做过自动化模拟，没人工走查。
  • 04玩法深度有限：无账号、社交、经济系统，留存靠不住。

验证密度是它值得被信任的理由；产品缺口是它还不该被推广的理由。

优劣势
07 完成度

能演示、能内测，
还不能当公开产品

模块状态说明
本地对战与三档 bot可用需自备 Postgres；一条命令起服务
观战与回放可用SSE 实时推送 + 逐手回退
链上对局可用Devnet，需 Phantom 与少量测试 SOL
链上棋谱馆可用公共 RPC 可能禁枚举，单局查询不受影响
形式化证明可用21 条定理，已进 CI，改规则即重证
托管服务端待补要让人「打开就能下」，还差一次部署
审计与主网未做主网前必须做，不能跳

08 怎么用

三类人，三条路

A / 只想玩

打开链接就能下

  1. 装 Phantom 钱包
  2. 网络切到 Devnet
  3. 领 1 SOL 测试币
  4. 建局，把地址发给对手
链上版不需要后端；本地版不需要钱包。
B / 本地跑

两条命令起服务

createdb nine_grid
cargo run -p nine-grid-server
打开 127.0.0.1:8080。migrations 自动执行，不用手工建表。
C / 看代码

三条命令验完

just check        # fmt/clippy/test
just chain-test   # 链上 10 项
just lean-verify  # 21 条定理
证明与实现不一致时，compare.sh 会逐行报出来。

链上版不需要后端，本地版不需要钱包 —— 两种模式共用同一份判胜规则，所以本地看到的胜负与链上一致。

09 现场演示

三分钟，四步

STEP 1

开一局，发邀请

首页点「开一局新棋」，拿到 6 位房间码与邀请链接。

30s
STEP 2

换窗口入座，三手判胜

无痕窗口打开链接自动执 X，落三手，看胜线与棋谱。

40s
STEP 3

切一次主题

右上角一键切「星穹会员」，同一份 DOM，只换变量。

10s
STEP 4

链上局与棋谱馆

连 Phantom 建局，再进棋谱馆展开这局，看它从交易里重建出来。

60s

兜底方案：链上 RPC 不稳时，直接放浏览器 E2E 的录屏，别在台上等网络。

10 下一步

还差三件事

01 / 半小时

真机走查

按文档在真 Phantom 上把签名弹窗点一遍。自动化模拟过，但真弹窗的文案与网络提示仍需人确认。

02 / 半天

托管一版服务端

接一个托管 Postgres，让人「打开就能下」。这是从「能演示」到「能给人用」的最低门槛。

03 / 不可控

审计与主网

主网前必须审计账户约束与结算逻辑；再补一点经济或积分设计，才有留下来的理由。

先把「能玩」做扎实，再谈「值得玩」。
